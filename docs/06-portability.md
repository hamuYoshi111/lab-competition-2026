# 配布の Makefile でビルドできることを確かめ、macOS で落ちる可能性のあった箇所を直した

主催者は配布の Makefile（`g++ -std=c++17 -O2 -Wall -Wextra`）で macOS か Linux 上でビルドすると考えられるが、ここまでは Windows の MSVC でしか確認していなかった。4 つの環境でビルドと実行を確かめ、見つかった 2 つの危ない箇所を直した。

**結論**

- 配布の Makefile のまま g++ 13・g++ 10・clang 18 でビルドでき、警告はゼロ、実行も正常。
- **小数の読み取りを環境に応じて切り替えるようにした**。macOS の標準コンパイラには「小数版の `std::from_chars`」が無く、そのままだとビルドできない恐れがあった。切り替えても読み取る値は同じで、速度の差は CSV 全体で 0.51 ミリ秒（2.31 → 2.82 ミリ秒。目安の 5 ミリ秒以内）。
- **Makefile の改行を LF にそろえた**。配布のものは Windows 式（CRLF）で、古い `make` では失敗しうる。
- MSVC 版と g++ 版では**結果が一致しない**。原因は計算の誤差ではなく、乱数の使われ方が処理系ごとに違うため。質の水準は同じ（10 種の平均で 0.00059 対 0.00062）。

## 1. どの環境で確かめたか

| 環境 | コンパイラ | ビルド方法 | 警告 | 実行 |
|---|---|---|---:|---|
| Windows 11 | MSVC 19.44.35228 | `build.bat`（`/std:c++17 /O2 /EHsc /utf-8`） | 0 | 正常 |
| WSL Ubuntu 24.04 | g++ 13.3.0 | 配布 Makefile（`make`） | 0 | 正常 |
| WSL Ubuntu 24.04 | clang++ 18.1.3 | 配布と同じオプション | 0 | 正常 |
| Docker `gcc:10` | g++ 10.5.0 | 配布 Makefile（`make`） | 0 | 正常 |

macOS の実機は手元に無いため、直接は確かめられていない。代わりに **g++ 10 を使った**。g++ 10 は macOS の標準コンパイラと同じく「小数版の `std::from_chars` が無い」環境なので、後述の切り替えが本当に働くかを実地で試せる。

## 2. 小数の読み取りを環境に応じて切り替えた

### 何が問題だったか

05 で CSV の読み込みを速くしたとき、文字列を数値に直す部品として `std::from_chars` を使った。これは C++17 の規格にある関数だが、**整数版はどの環境にもあるのに、小数版は用意された時期が処理系ごとに大きく違う**。macOS の標準コンパイラ（Apple clang）と、g++ 11 より前には小数版が無い。無い環境では「そんな関数は無い」というエラーになり、ビルドそのものが通らない。

提出物が動かないのは、質や速さの前に致命的なので、ここを最優先で直した。

### どう直したか

`csv_loader.cpp` に、**小数版の `from_chars` がこの環境に実在するかをコンパイル時に調べる仕組み**を入れた。無ければ C 言語の `strtod`（配布コードが使っていた `std::stod` の中身そのもの）に切り替わる。判定は二重にしている。

1. 標準が定める「用意できています」の印である `__cpp_lib_to_chars` が `201611` 以上か。
2. 実際に `std::from_chars(..., double&)` を呼べるか（テンプレートの仕組みで、呼べなければ静かに「無い」と判定される）。

両方そろったときだけ `from_chars` を使い、片方でも欠ければ `strtod` に落ちる。安全側に倒してある。

どちらを通っても読み取れる値は同じである。`from_chars` も `strtod` も「書かれた10進数にいちばん近い double」に丸める規則が同じだからで、実際に両方の経路で出力を比べて 1 ビットも違わないことを確認した。

動作確認用に `uses_float_from_chars()` を公開した。どちらの経路を通ったかを外から確かめられる。

### どの環境がどちらを通ったか

| 環境 | `__cpp_lib_to_chars` | 通る経路 |
|---|---|---|
| MSVC 19.44 | 201611 | `from_chars` |
| g++ 13.3 | 定義あり | `from_chars` |
| clang++ 18.1 | 定義あり | `from_chars` |
| g++ 10.5 | **未定義** | **`strtod`** |

g++ 10.5 は配布 Makefile で警告ゼロのままビルドでき、実行結果も g++ 13 と同じ評価値（種42 で 0.000314）になった。切り替えが実際に働いている。

### 速度への影響

MSVC・種42・5回実行のうち、1回目（ファイルがディスクキャッシュに乗る前）を除く4回の平均。単位はミリ秒。

| 項目 | `from_chars` | `strtod` | 差 |
|---|---:|---:|---:|
| 地点CSV（113行） | 0.154 | 0.164 | +0.01 |
| ノードCSV（2267行） | 0.418 | 0.547 | +0.13 |
| エッジCSV（6860行） | 1.675 | 2.045 | +0.37 |
| **CSV読み込み 合計** | **2.312** | **2.822** | **+0.51** |

目安として置いた「5 ミリ秒を超えない」は満たしている。総時間 106 ミリ秒に対して 0.5 ミリ秒なので、`strtod` に落ちる環境でも実質的な差は出ない。

なお、この切り替えは「使われない側の関数」が残らないように書いてある。素直に書くと clang が「使わない関数がある」と警告を出すため、テンプレートにして必要なときだけ組み立てられるようにした。

## 3. Makefile の改行を LF にそろえた

配布の Makefile は Windows 式の改行（CRLF）で書かれている。Linux の `make`（GNU Make 4.x）は行末の CR を取り除くので問題なく通ったが、**古い GNU Make は CR をコマンドの一部として扱う**。macOS に標準で入っている `make` は古い版（3.81）なので、ここで失敗する可能性がある。

手元に macOS が無いので実機では確かめられていない。ただし LF にそろえておけば Windows・Linux・macOS のどれでも通るので、`lab-competition-2026/Makefile` を LF に直した。あわせて `.gitattributes` を置き、git 経由で取り出しても LF のままになるようにした（この作業フォルダは `core.autocrlf=true` なので、指定が無いと Windows 側で CRLF に戻ってしまう）。

配布元の `upstream/` は変更していない。

## 4. その他の移植性チェック

| 確認項目 | 結果 |
|---|---|
| `<windows.h>` の取り込み | `main.cpp` の 1 か所のみ。`#ifdef _WIN32` で囲まれている。中で呼ぶ `SetConsoleOutputCP` も同じ囲みの中 |
| `std::filesystem` の追加リンク | 不要。g++ 9 以降は標準ライブラリに入っている。g++ 10・g++ 13・clang 18 で `-lstdc++fs` 無しでリンクできた |
| `long long` の printf 書式 | `%lld` は使っていない。printf 系は `std::snprintf(buf, sizeof(buf), "%.*f", int, double)` の 1 か所だけ |
| ヘッダ名の大文字小文字 | すべて小文字で、実ファイル名と一致。大文字小文字を区別するファイルシステムでも問題ない |
| ソースの文字コード | UTF-8。MSVC は `build.bat` の `/utf-8`、g++ と clang は既定が UTF-8 |
| `tests/` のビルド | `local_search_test` と `efficiency_test` は g++ でもビルドでき、どちらも PASS。`speedup_test` は `-DSPEEDUP_INDEXED` を付けないと通らない（03 の比較用で、マクロ無しの側は 03 以前の関数を呼ぶ古い分岐）。Makefile の対象外なので提出物には影響しない |

## 5. MSVC 版と g++ 版で結果が一致しないこと

同じ種（42）・同じ設定で実行しても、最終的なコースが違う。

| | MSVC | g++ 13 |
|---|---:|---:|
| 評価値 E | 0.000593 | 0.000314 |
| 地点数 | 8 | 8 |
| 道のり | 3371.3 m | 3387.4 m |
| 累積登り | 48.4 m | 47.2 m |
| 1世代目の最良値 | 0.001001 | 0.002502 |

**1世代目から違う**ことが原因の手がかりになる。浮動小数点の丸め誤差なら世代を重ねるうちに少しずつずれるはずで、最初の集団から違うのは乱数の側の問題である。

C++ の規格は、乱数の種から整数列を作る部分（`std::mt19937`）については「どの処理系でも同じ列を出すこと」と決めている。しかし、その整数列を「0〜11 の一様な整数」や「0〜1 の一様な小数」に加工する部分（`std::uniform_int_distribution`、`std::uniform_real_distribution`、`std::shuffle`）については、**どう加工するかを決めていない**。MSVC と g++ の標準ライブラリは違うやり方を採っているので、同じ種でも違う個体が出てくる。

これは誤りではなく、「同じ種で同じ結果」が保証される範囲が処理系の中だけ、というだけである。質の水準は変わらない。

| | E平均 | E標準偏差 | E最小 | E最大 |
|---|---:|---:|---:|---:|
| MSVC（種1〜10） | 0.00059 | 0.00049 | 0.00013 | 0.00163 |
| g++ 13（種1〜10） | 0.00062 | 0.00072 | 0.00010 | 0.00260 |

g++ の標準偏差がやや大きいのは、種1 の結果（0.0026）が 1 つだけ大きかったため。10 回の測定ではこの程度は普通にぶれる。

g++ 10 と g++ 13 の間でも差が出た。種42 では、**選んだ 8 地点と評価値（0.000314）は完全に同じで、巡る向きだけが逆**だった。同じ質の解に別の書き方で着いている。

**この差を消すこともできる**。分布の部分を自分で書けば、どの処理系でも同じ結果になる。今回は入れていない。質の水準に差が出ないことを 10 種で確かめられたのと、分布を自作すると 04・05 で積み上げた比較の前提（同じ種で同じ結果）を全部引き直すことになるためである。主催者側の 10 回の結果が手元の数値と一致しない点は、残る不確かさとして記録しておく。

## 6. 残るリスク

- **macOS の実機で確かめていない**。手元に Mac が無い。`std::from_chars` の件は g++ 10 で代替確認したが、Apple clang 固有の問題（たとえばヘッダの取り込み順やライブラリの版の指定）までは潰せていない。
- Apple clang の `<filesystem>` は macOS 10.15 以降でしか使えない。それより古い macOS でビルドされると `std::filesystem::create_directories`（出力フォルダの作成）が通らない。使っているのはこの 1 か所だけなので、必要なら `mkdir` 相当に置き換えられる。
- 主催者の環境での 10 回の結果は、乱数の違いにより手元の数値とは一致しない。

## 7. 再現手順

```sh
# g++（WSL / Linux / macOS 共通）
cd lab-competition-2026
make clean && make
./orienteering

# 小数の読み取りを強制的に strtod 側にして比べる（検証用）
g++ -std=c++17 -O2 -Wall -Wextra -DORIENTEERING_NO_FLOAT_FROM_CHARS \
    -o orienteering_strtod csv_loader.cpp graph.cpp evaluate.cpp ga.cpp main.cpp

# 小数版 from_chars が無い環境の再現（Docker）
docker run --rm -v <このフォルダ>:/w gcc:10 bash -c "cp -r /w/lab-competition-2026 /b && cd /b && make && ./orienteering"
```
