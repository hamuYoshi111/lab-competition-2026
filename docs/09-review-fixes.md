## 1. 表を引く評価の厳密一致テストを復活させた (指摘: tests-1 / high)

**何が問題だったか**: 探索が実際に通る評価の経路は 2 つある。GA の中では
「地点の番号で表を引く」速い経路を通り、配布プログラムと同じ計算をする「参照の経路」は
比較用に残してある。この 2 つが同じ値を返すことを確かめるテストは
`tests/speedup_test.cpp` にしかなく、そのファイルは関数の引数が変わったせいで
ビルドできなくなっていた。しかもどのビルド手順にも入っていないので、
誰も壊れていることに気づけない。つまり `best_course.json` に出る距離・登り・
4 つの目的関数の値は、どのテストも通っていない経路から出ていた。

**どう直したか**: 常に走る `tests/local_search_test.cpp` に検査を移した。

- 地点数 6〜12 のランダムな巡回順 1,050 件と、ランダムな染色体 200 件の計 1,250 件について、
  表を引く評価と参照の評価の「E・総距離・累積登り・4 つの目的関数・選んだ地点・通ったノード」が
  すべて厳密に (誤差を許さず) 一致することを確かめる
- 表の近接罰点が元の計算式と一致すること、巡回順の直接評価が染色体経由の評価と一致することも確かめる
- 経路が 1 本もない状態 (到達不能) でも、両方が同じペナルティを返すことを確かめる
- 人工の道路網 (6 点・7 本) で、同じ 2 点を結ぶ道が 2 本あるとき・到達できない孤立点があるとき・
  存在しない出発点を指定したとき・経路表に無い地点を引いたときの答えが想定どおりかを確かめる

人工の道路網の期待値は、実装の取り決めをそのまま数値で書き下した。たとえば同じ 2 点を結ぶ道が
2 本あるとき、距離は短い方を使うが登りは「入力ファイルで先に出てきた方」を使う。
これは配布プログラムから受け継いだ仕様で、テストがその形を固定する。

`tests/local_search_test.cpp` には失敗時の表示も足した。以前は検査に落ちると何も表示せずに
異常終了していたので、何が失敗したのか分からなかった。今は `FAIL: 理由` を出して終了コード 1 を返す。

**`tests/speedup_test.cpp` は残した**。これは「変更の前後で 1 ビットも変わっていない」ことを
16 進表記の全文照合で確かめる比較専用の道具で、`tools/verify_speedup.py` と
`tools/verify_overhead.py` が古いソースに対してもビルドするため、古い呼び出しの分岐が
意図的に残っている。役割が分かるよう、ファイルの先頭にその説明を書いた。

**確認**: `test.bat` の表示が `PASS: 19560 courses; ...; 1250 table-vs-reference exact matches; artificial graph`
になった。バイト比較は一致。

## 2. 無効な解を書き出さないようにした (指摘: correctness-1 / medium)

**何が問題だったか**: 有効なコースが 1 つも作れなかった場合 (道路網が分断されていて、
正門から行き来できる候補が 6 か所に満たないなど)、プログラムは無効解を表す「実在しない巨大な数」
をそのまま JSON に書いていた。しかも整形用の入れ物が 64 バイトしかないため、その巨大な数は
途中で切れて「1.797…e62」のような、もっともらしい別の数値として記録される。
JSON としては正しい形なので後段の採点でも気づけず、終了コードも 0 (成功) だった。

**どう直したか**: 全部のやり直しを終えた時点で最良解が無効なら、標準エラーに
「有効なコースが見つかりませんでした (到達可能な候補が 6 か所未満など)」と出し、
ファイルを 1 つも書かずに終了コード 1 で終わる。あわせて整形用の入れ物を 400 バイトに広げ、
どんな値でも途中で切れないようにした (今回の変更で無効解が書かれることはなくなったが、安全弁として残す)。

**確認**: `edges.csv` を見出し行だけにした入力で実行すると、上のメッセージが出て終了コード 1 になり、
`output/` フォルダ自体が作られないことを確かめた。通常のデータではバイト比較が一致。

## 3. JSON に書く文字列を安全にした (指摘: security-1 / medium)

**何が問題だったか**: 地点名と種別を、前後に二重引用符を足すだけで JSON に書いていた。
主催者のデータの地点名に二重引用符や逆斜線が 1 つ入っているだけで JSON が壊れて読めなくなる。
さらに悪い場合として、地点名を細工すると、本来の E の値より後ろに別の `"fitness"` を
割り込ませることができる。多くの JSON 読み取りは後に出た方を採るので、採点に使う値を
すり替えられてしまう。

**どう直したか**: 逆斜線・二重引用符・制御文字 (0x00〜0x1F) を JSON の決まりどおりに
置き換える関数を通してから書くようにした。改行やタブは `\n` `\t` に、それ以外の制御文字は
`\u00XX` にする。

**確認**: 全地点の名前を `X" }] \ (タブ)(制御文字)attack`、種別を `f"e\a` に差し替えた入力で実行し、
出力が Python の `json.load` で問題なく読め、読み取った文字列が元の文字列と一致することを確かめた。
通常のデータではバイト比較が一致 (既存のデータにはエスケープが要る文字が無いため、出力は 1 バイトも変わらない)。

## 4. 引数の読み取りを 1 か所にまとめた (指摘: correctness-3 / maintainability-7)

**何が問題だったか**: 引数の解釈が 3 か所に分かれていた。個体数と世代数は最初に、
オプションは 4 番目の引数から、種は CSV の読み込みと最短経路の事前計算がすべて終わったあとに
読んでいた。そのため

- `orienteering.exe --restarts 3` のようにオプションだけを付けると、オプションは黙って無視され、
  固定費 (0.02 秒ほどの読み込みと事前計算) を払い終わってから
  「エラー: stoul」という意味の分からない表示で落ちた
- 種に数字でない文字列を渡した場合も同じく、すべて読み込んでから落ちた

**どう直したか**: `main.cpp` に設定をまとめた 1 つの型と、1 つの解析関数を置いた。
`argv[1]` から順に見て、`--` で始まれば オプション、それ以外は前から順に 種・個体数・世代数 として読む。
値が読めない・範囲外・知らないオプションのときは、CSV を読む前に使い方を表示して終了コード 2 で終わる。
個体数と世代数の既定値は `const.h` だけが持つことにし、`ga.h` の `run_ga` に書いてあった
同じ既定値は消した (呼び出し側が必ず値を渡す)。

**確認**: 次の 3 通りが同じ `best_course.json` を出すことをバイト比較で確かめた。

```
orienteering.exe
orienteering.exe 42 10 20 --restarts 3
orienteering.exe --restarts 3
```

誤った引数 (`--nope` / `abc` / `42 0` / 値のない `--restarts`) では、いずれも入力を読む前に
理由と使い方を表示して終了コード 2 で終わることを確かめた。

## 5. 推定所要時間の式を 1 か所にまとめた (指摘: maintainability-2 / medium)

**何が問題だったか**: 「距離と登りから所要時間 (分) を出す」式が 4 か所に手書きされていた。
うち 2 か所は `main.cpp` の中にあり、JSON に書く値と画面に出す値を別々に計算していた。
片方だけ直すと表示と出力が食い違う。

**どう直したか**: `evaluate.h` に `estimated_minutes(距離, 登り)` を置き、
JSON 出力・画面表示・貪欲な初期解づくりの 3 か所から呼ぶようにした。

**4 か所目 (`f_time`) はあえて寄せていない**。`f_time` だけは
`(距離/速さ)*60 + (登り/速さ)*60` の順で足しており、他の 3 か所の
`(距離/速さ + 登り/速さ)*60` とは丸めの回数が 1 回違う。これは配布プログラムから
そのまま受け継いだ形で、式を揃えると評価値が最後の 1 ビットで変わり、答えが変わる恐れがある。
どちらのソースにもその理由をコメントで書いた。

**確認**: バイト比較が一致。

## 6. 近接罰点の差分計算 — **見送った** (指摘: performance-1 / medium)

**何をしようとしたか**: 局所探索は近傍のコースを 1 つ評価するたびに、
「地点どうしが近すぎる罰点」を全ペア (8 地点なら 28 組) 数え直している。
ところが 2-opt と Or-opt は地点の集合が変わらず順番を入れ替えるだけなので、
罰点の合計は現在のコースと同じはずである。地点の追加・削除・置換も、
変わるのは 1 地点ぶんだけなので、その行だけ足し引きすれば足りる。

**やってみた結果**: **答えが変わった**。種 10 で E が 0.000756 から 0.002332 に悪化し、
選ぶ地点も総距離も別のものになった。

原因は計算違いではなく、**足し算の順序**である。同じ数の集まりでも足す順を変えると、
小数の丸めの都合で答えが最後の 1 ビットだけ変わることがある。
差分計算の途中経過を全部照合したところ、1 回の実行で 22 万回、
「正しく数え直した値」と「差分で求めた値」が最後の 1〜2 ビットだけ違っていた。
局所探索は「今の best より厳密に小さいか」で手を選ぶので、この 1 ビットの差が
たまたま同点付近にあった手の採否をひっくり返し、そこから先の探索が丸ごと別の道を進む。

**指示どおり縮小版も試した**: 追加・削除・置換は今までどおり数え直し、
地点の集合が変わらない 2-opt と Or-opt だけ現在の値を使い回す形。
こちらは種 1〜10・種 42・引数なしのすべてでバイト比較が一致した。
ただし採用しなかった。理由は 2 つ。

1. **速くならない**。局所探索が 1 回の改善で調べる近傍は約 1,400 件で、そのうち
   2-opt と Or-opt は 84 件 (6%) しかない。残り 94% は追加と置換なので、
   省ける計算はごくわずかである。実測でも、世代ループの時間は 0.1255 秒 (変更前) に対し
   0.1274 秒 (変更後) で、測定のばらつきに埋もれて差が出なかった (15 回ずつの中央値)。
2. **1 ビットも変わらない保証が無くなる**。縮小版でも 1 回の実行で 4,000 回ほど
   最後の 1 ビットの違いが出ている。今回のデータではたまたま手の選び方が変わらなかっただけで、
   主催者のデータでも変わらない保証は無い。このプロジェクトは「速くしても答えは 1 ビットも変えない」
   を通してきたので、得るものが無いのにその保証だけ捨てるのは割に合わない。

**結論**: この項目は見送り、コードは元のままにした。`ga.cpp` の該当箇所に、
試して見送った経緯を 2 行のコメントで残した。
指摘そのものは「ここを速くする余地がある」という指摘としては正しく、
もし将来ここを本当に速くしたいなら、足す順を変えない形 (たとえば整数化して足す) が必要になる。

## 7. 壊れた CSV の行に警告を出すようにした (指摘: security-2 の縮小版 / low)

**何が問題だったか**: 列が足りない行は黙って読み飛ばし、数値の後ろに余分な文字があっても
(`12abc` を `12` として) 黙って通していた。入力ファイルが壊れていても何も言わずに
別のデータで計算が進んでしまう。

**どう直したか**: 例外にはせず (寛容なままにして)、標準エラーに行番号付きの警告を 1 行出す。
主催者のデータに些細な書き方の違いがあったときに落ちる方が危ないので、動作は変えていない。

```
警告: input/nodes.csv の 4 行目: 列が足りないので読み飛ばしました
警告: input/nodes.csv の 6 行目: 数値の後ろに余分な文字があります（読めたところまでを使いました）
```

**確認**: 配布データと加工データ 7 種の計 8 データすべてで、警告が 1 行も出ないことを確かめた
(標準エラーの出力が 0 バイト)。`nodes.csv` の 1 行から列を削り、別の行の数値の後ろに文字を足した
入力では、上の 2 行が出ることを確かめた。バイト比較は一致。

## 直さなかった指摘

レビューの 27 件のうち、下記は締切までの時間と「動作確認済みのコードを触る危険」を
天秤にかけて見送った。報告書に残してある。

- 局所探索の有無を実行時フラグにする (`USE_LOCAL_SEARCH` は今もコンパイル時の定数)

- `Graph` の使い終わったメンバを消す

## 残した課題

- 近接罰点の差分計算は見送った (上記 6)。局所探索の内側を本当に速くするには、
  足す順が変わらない形にする必要がある。
- 引数の解析は「数字は前から順に 3 つまで」という決まりにしたので、
  たとえば個体数だけを変えたいときは種も書く必要がある (`orienteering.exe 42 20`)。
- JSON のエスケープは文字列 2 列 (名前・種別) にしか効かない。数値と経路は
  整数と `snprintf` で書いているので元から安全である。
- CSV の警告は「列不足」と「数値の後ろの余分な文字」の 2 種類だけ。
  項目の中にカンマが入って列がずれる場合 (RFC4180 の引用符) は今も解釈しない。
- 処理時間の測定は Windows・MSVC のみ。g++ 側は動作確認だけで時間は測っていない。
